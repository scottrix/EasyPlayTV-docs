Troubleshooting & known issues

Recipes for symptoms observed in production. Each entry follows the form symptom → cause → fix → reference into the docs. Most of these have already been patched in the source; the page is here so a future maintainer can recognize the failure mode quickly.

Database & sync

"Packet sequence number wrong - got 2 expected 1"

Cause: two provider-sync daemon threads sharing the same pymysql connection. The MySQL protocol is per-connection; interleaved packets from two threads corrupt each other.

Fix: each worker thread owns its own connection. The implementing code in library_sync._get_db uses threading.local() + an explicit only main thread can fall back to the legacy module-level _sync_db guard. Don't break the threading.main_thread() check — the old fallback that always grabbed _sync_db for any thread was the source of the original corruption.

"'NoneType' object has no attribute 'read'"

Cause: same thing from the other thread's perspective — its socket reader got closed out from under it by the other thread's ping() failure.

Fix: same — per-thread connections.

Empty/un-prefixed duplicate tvshow rows appearing

Cause: Kodi's TMDB scanner recursing into the addon's plugin URL or legacy disk-folder path rows after a migration that didn't set exclude=1.

Fix: ensure library_sync.ensure_series_path_config has run (it's called at the start of every sync_series_direct run). If duplicate rows already exist, run ?action=prefix_titles from the UI to retrofit [PROVIDER] prefixes — see the prefix_existing_tvshows function.

TV show row with 0 episodes despite a real TMDb match

Cause: a sync run that inserted the tvshow row but the provider's list_episodes call threw an exception (transient HTTP failure or partial outage). The historical bug was that the insert happened before the episode fetch — even if episodes failed the show row was empty forever.

Fix: the order was switched. Now sync_series_direct fetches episodes before calling _insert_tvshow. If the fetch fails the show is simply skipped on this run and retried next 6h slot.

Empty show rows in DB with no episodes (legacy)

Cause: shows first synced by an older version that inserted-then-fetched — leftover from before the order switch.

Fix: run ?action=backfill_art from the UI (it doesn't add episodes but matches shows with valid TMDb ids and clears some metadata); the next sync will re-fetch episodes. For stubborn cases drop and re-sync the specific show: delete from tvshow WHERE idShow = ; delete from tvshowlinkpath, genre_link, uniqueid, art with the same idShow; then trigger a sync for that provider.

STV single-episode documentaries missing from library

Cause: STV returns episodes with episode_number=0 when playerSeries is null (no per-episode metadata). The sync_series_direct insert loop drops episode_number=0 via the if en_int < 1: continue guard. Documentaries + entire programmes without per-episode index info (Coronation Street, Emmerdale daily strips) were silently dropped.

Fix: a renumber pre-pass in sync_series_direct at lines 858-888 sequentially renumbers episode_number=0 episodes from 1 within their season block. If season is also 0/missing, it's bumped to 1 so the show appears as Season 1 rather than the Kodi specials block (S00). The cataloguer doesn't lie about the episode numbers; the sync engine's renumber is the workaround for STV's incomplete metadata.

"Buried" C4 show appears as "Buried Hearts" — the same show fragmenting into two rows

Cause: TMDb's search-by-title can re-rank similar-named siblings. C4's Buried → TMDb returns Buried Hearts with a different tmdb_id. Each subsequent sync resolves the title to the new canonical name and inserts episodes into the new row, orphaning the original [C4] Buried row forever.

Fix: _insert_tvshow prefers the [PROVIDER] (the local safe_title dir-name key) over the [PROVIDER] when looking up an existing show. Falling back to TMDb canonical is allowed for legacy rows created before this fix. The primary lookup must remain the dir-name one.

Long-running C4 shows (Come Dine with Me, The Bill) lose their episodes

Cause: these daily strips produce __PARAMS__ JSON blocks over 600 KB. The c4_vod._extract_brand_data walker used to cap its scan at 1 MB; lines longer than the cap silently dropped the brand data and fell through to "no episodes".

Fix: the cap was raised to 4 MB (line 50). If you see a bigger show, also bump the cap; the regex still bails at the first } that returns the brace depth to 0, so the cap is only a safety bound.

Playback

ITVX playback: 403 "Failed to authenticate HMAC" repeatedly

Cause: not actually an ITVX issue — this is the My5 symptom that's been mismarbled in your logs. If you're seeing it on My5 (Cassie) the cause is the C5 player JS has rotated the AES/HMAC keys, and the addon's cached key is the previous one.

Fix: my5._fetch_cassie already self-heals this — on a 403 with body "Failed to authenticate HMAC" it re-extracts keys from the live C5 player JS and retries once. If you're still seeing 403s after that, the path https://player.akamaized.net/html5player/core/html5-c5-player.js is no longer the right URL — C5 may have moved hosts. Check the network tab of the C5 web player to find the new JS bundle URL.

ITVX playback: "session expired - sign in again"

Cause: refresh token expired (they live ~30 days). The user's saved credentials in addon settings are still valid but the refresh-token grant needs a fresh login.

Fix: open the addon's settings, ITVX section, sign out, then sign in via the addon's main menu "Sign in to ITVX" item. The addon calls itvx.login which uses the password grant directly (the cookie-based web flow isn't used because the API directly accepts password grant for the app.10ft.itv.com origin).

Sky News playback: "this content is not available in your region"

Cause: Brightcove's policy key rotation ignored the X-Forwarded-For: 2.97.0.0 header sky.resolve sends. The current Sky policy may not trust the XFF header anymore; the addon would start returning AU/US manifest URLs that don't play on a UK Kodi box.

Fix: if you're not on a UK IP, the addon has no remedy — Sky News only ships a UK stream. Run from a UK-IP egress (a VPN at the network layer) instead of relying on the XFF spoof. The spoof was always a per-policy brittle workaround.

Blaze shows empty catalogue

Cause: Blaze's HTML page scraper (blaze_vod.list_shows) regexes broke — Blaze changed class names or HTML structure on their static page.

Fix: open https://watch.blaze.tv/series in a browser, view source, grep for col-auto layout-carousel-column. If the class names changed, update the regex at blaze_vod.list_shows line 13 and the per-card regexes (lines 15-40). No JSON-API fallback exists.

OSMC / Pi-specific hardware

"EGL_BAD_SURFACE" with ITVX Widevine content on OSMC

Cause: inputstream.adaptive's secure-decoder path is broken on the Pi's V4L2 mem2mem hardware decoder — it tries to allocate secure surfaces that the Pi's V4L2 path can't honour, fails with EGL_BAD_SURFACE, and bails out of playback entirely.

Fix: set NOSECUREDECODER=true in inputstream.adaptive's settings on OSMC to force the V4L2 mem2mem hardware decoder instead of the broken secure decoder path for ITVX Widevine content. improves ITVX startup time dramatically on the Pi: ~5-8 s from click-to-play rather than the 30-60 s of EGL dithering.

~13 min startup delay after Kodi reboot

Cause: a prior EasyPlayTV run had propagated a malformed unquoted XML true to EasyPlayTV's parent Series path row in MyVideos.path. With verboselog=true, Kodi's TMDb scraper dumps 20K+ log lines per /tv//season/N API call (pformat of the entire JSON response), costing ~22 s per season on RPi SD-card I/O — e.g. ~13 min for WWE Raw alone (35 seasons).

Fix: library_sync._sanitize_scraper_settings_xml quotes unquoted attributes and pins verboselog=false; called from _repair_scraper_path_settings (run once on every migrate_to_plugin_paths). If you see verbose log spam after a Kodi upgrade, run ?action=sync manually to re-fire the repair.

Manual syncs / external triggers

JSON-RPC Addons.ExecuteAddon ignored params (Kodi 21+)

Cause: Kodi 21's Addons.ExecuteAddon no longer invokes python.pluginsource addons with query-string params via JSON-RPC — it loads the addon's default entry-point without forwarding argv. RunPlugin is similarly unreliable.

Fix: use the marker-file mechanism in service.py:_check_force_markers instead. Touch a file at /force_sync_ (e.g. force_sync_c4). The service polls every 30 s and fires the sync when it sees the marker; latency at worst half a minute. From a shell: touch /home/osmc/.kodi/userdata/addon_data/plugin.video.easyplaytv/force_sync_c4.

Manual sync via JSON-RPC kills the daemon thread

Cause: if you trigger ?action=sync&provider=c4 (fire-and-forget mode, no blocking=1) over JSON-RPC, the daemon thread spawned dies the moment the calling script returns — JSON-RPC RunPlugin tears down the interpreter that owns the daemon.

Fix: always use ?action=sync&provider=c4&blocking=1 from JSON-RPC, OR use the marker-file approach above. From the addon's own UI menu it's fine without blocking because the navigation thread isn't torn down.
