Troubleshooting & known issues

Recipes for symptoms observed in production. Each entry follows the form symptom → cause → fix → reference into the docs.

Database & sync

"Packet sequence number wrong - got 2 expected 1"

Cause: two provider-sync daemon threads sharing the same pymysql connection. The MySQL protocol is per-connection; interleaved packets from two threads corrupt each other.

Fix: each worker thread owns its own connection. The implementing code in library_sync._get_db uses threading.local() + a guard that only the main thread can fall back to the module-level _sync_db. Don't break the threading.main_thread() check — any path that lets a worker thread pick up _sync_db reintroduces the corruption.

"'NoneType' object has no attribute 'read'"

Cause: same thing from the other thread's perspective — its socket reader got closed out from under it by the other thread's ping() failure.

Fix: same — per-thread connections.

Empty/un-prefixed duplicate tvshow rows appearing

Cause: Kodi's TMDB scanner recursing into the addon's plugin URL path row, or into a disk-folder path row that hasn't been marked exclude=1.

Fix: ensure library_sync.ensure_series_path_config has run (it's called at the start of every sync_series_direct run). If duplicate rows already exist, run ?action=prefix_titles from the UI to retrofit [PROVIDER] prefixes — see the prefix_existing_tvshows function.

TV show row with 0 episodes despite a real TMDb match

Cause: the provider's list_episodes call threw an exception (transient HTTP failure or partial outage). The sync insert guard skips shows with no episodes, but if the fetch fails the show stays out of the library until the next sync slot.

Fix: sync_series_direct fetches episodes before calling _insert_tvshow. If the fetch fails the show is simply skipped on this run and retried next 6h slot.

Empty show rows in DB with no episodes

Symptom: old tvshow rows visible in Kodi's library with poster and metadata but zero episodes underneath.

Cause: the rows were inserted by a sync run whose subsequent episode fetch failed partway through — the show exists but the episode rows were never written.

Fix: run ?action=backfill_art from the UI (it doesn't add episodes but matches shows with valid TMDb ids and clears some metadata); the next sync will re-fetch episodes. For stubborn cases drop and re-sync the specific show: delete from tvshow WHERE idShow = ; delete from tvshowlinkpath, genre_link, uniqueid, art with the same idShow; then trigger a sync for that provider.

STV single-episode documentaries missing from library

Cause: STV returns episodes with episode_number=0 when playerSeries is null (no per-episode metadata). The sync_series_direct insert loop drops episode_number=0 via the if en_int < 1: continue guard, so documentaries and entire programmes without per-episode index info (Coronation Street, Emmerdale daily strips) would be missing from the library.

Fix: a renumber pre-pass in sync_series_direct at lines 858–888 sequentially renumbers episode_number=0 episodes from 1 within their season block before the insert loop runs. If season is also 0/missing, it's bumped to 1 so the show appears as Season 1 rather than the Kodi specials block (S00).

"Buried" C4 show appears as "Buried Hearts" — the same show fragmenting into two rows

Cause: TMDb's search-by-title re-ranks similar-named siblings dynamically. C4's Buried → TMDb can return Buried Hearts with a different tmdb_id on a different day. Each subsequent sync resolves the same title to a different canonical name and inserts episodes into the new row, fragmenting one show across multiple tvshow rows.

Fix: _insert_tvshow prefers the [PROVIDER] (the local safe_title dir-name key) over the [PROVIDER] when looking up an existing show. The primary lookup is the dir-name one; the TMDb canonical name is only used as a fallback if no dir-name match is found. This keeps the local show identity stable across TMDb re-ranks.

Long-running C4 shows (Come Dine with Me, The Bill) lose their episodes

Cause: these daily strips produce __PARAMS__ JSON blocks over 600 KB. The c4_vod._extract_brand_data walker caps its scan at 4 MB; lines longer than the cap silently drop the brand data and fall through to "no episodes".

Fix: the cap sits at line 50 — raise it if you see a bigger show. The regex still bails at the first } that returns the brace depth to 0, so the cap is a safety bound, not the correctness boundary.

Playback

ITVX playback: 403 "Failed to authenticate HMAC" repeatedly

Cause: not actually an ITVX issue — this is the My5 symptom that's been mismarbled in your logs. If you're seeing it on My5 (Cassie) the cause is the C5 player JS has rotated the AES/HMAC keys, and the addon's cached key is the previous one.

Fix: my5._fetch_cassie already self-heals this — on a 403 with body "Failed to authenticate HMAC" it re-extracts keys from the live C5 player JS and retries once. If you're still seeing 403s after that, the path https://player.akamaized.net/html5player/core/html5-c5-player.js is no longer the right URL — C5 may have moved hosts. Check the network tab of the C5 web player to find the new JS bundle URL.

ITVX playback: "session expired - sign in again"

Cause: refresh token expired (they live ~30 days). The user's saved credentials in addon settings are still valid but the refresh-token grant needs a fresh login.

Fix: open the addon's settings → ITVX section → sign out, then sign in again. The addon calls itvx.login which uses the password grant directly (the cookie-based web flow isn't used because the API directly accepts password grant for the app.10ft.itv.com origin).

My5 premium content: 401 / 403 Bearer rejected on every playback

Cause: the saved Cognito session in addon_data/plugin.video.easyplaytv/my5_session has expired and the refresh token can no longer renew the access token (Cognito refresh tokens stay valid until revoked by GlobalSignOut, but server-side session invalidation can still revoke them — e.g. if you sign out via the My5 website).

Fix: open the addon's settings → Channel5 section → sign out, then sign in again. The addon calls my5.login which InitiateAuth(USER_PASSWORD_AUTH)'s against AWS Cognito directly and persists a fresh session dict (containing a new refresh_token) to my5_session. Note that free-to-air content will keep playing in the meantime — the _fetch_cassie retry logic drops the Authorization: Bearer header on 401/403 and re-issues the request anonymously.

My5 account challenge not supported: "SOFTWARE_TOKEN_MFA" / "NEW_PASSWORD_REQUIRED" / etc.

Cause: the Cognito InitiateAuth response came back with a ChallengeName instead of an AuthenticationResult. My5's hosted-UI web flow handles these (MFA, new-device, SRP, password-reset) but the addon's direct USER_PASSWORD_AUTH path does not.

Fix: sign in to channel5.com in a browser first and complete the challenge there. Once the account is in a state Cognito accepts for direct USER_PASSWORD_AUTH (typically: MFA disabled, password confirmed), the addon's ?action=my5_login will succeed and persist the session locally.

Sky News playback: "this content is not available in your region"

Cause: Brightcove's policy key rotation can ignore the X-Forwarded-For: 2.97.0.0 header sky.resolve sends. When the current Sky policy stops trusting the XFF header, the addon returns AU/US manifest URLs that don't play on a UK Kodi box.

Fix: if you're not on a UK IP, the addon has no remedy — Sky News only ships a UK stream. Run from a UK-IP egress (a VPN at the network layer) instead of relying on the XFF spoof. The XFF spoof is a per-policy workaround; assume it can break on any policy rotation.

Blaze shows empty catalogue

Cause: Blaze's HTML page scraper (blaze_vod.list_shows) regexes broke — Blaze changed class names or HTML structure on their static page.

Fix: open https://watch.blaze.tv/series in a browser, view source, grep for col-auto layout-carousel-column. If the class names changed, update the regex at blaze_vod.list_shows line 13 and the per-card regexes (lines 15-40). No JSON-API fallback exists.

OSMC / Pi-specific hardware

"EGL_BAD_SURFACE" with ITVX Widevine content on OSMC

Cause: inputstream.adaptive's secure-decoder path is broken on the Pi's V4L2 mem2mem hardware decoder — it tries to allocate secure surfaces that the Pi's V4L2 path can't honour, fails with EGL_BAD_SURFACE, and bails out of playback entirely.

Fix: set NOSECUREDECODER=true in inputstream.adaptive's settings on OSMC to force the V4L2 mem2mem hardware decoder instead of the broken secure decoder path for ITVX Widevine content. ITVX startup drops to ~5–8 s from click-to-play rather than the 30–60 s of EGL dithering.

~13 min startup delay after Kodi reboot

Cause: a stray malformed (unquoted XML) verboselog=true setting in the EasyPlayTV parent Series path row of MyVideos.path. Kodi's TMDb scraper logs 20K+ lines per /tv//season/N API call when the setting is on (pformat of the entire JSON response), costing ~22 s per season on RPi SD-card I/O — e.g. ~13 min for WWE Raw alone (35 seasons).

Fix: library_sync._sanitize_scraper_settings_xml quotes unquoted attributes and pins verboselog=false; called from _repair_scraper_path_settings on every migrate_to_plugin_paths run. If you see verbose log spam after a Kodi upgrade, run ?action=sync manually to re-fire the repair.

Kodi crashes 3× in 5 minutes after reboot on Pi 4 / Pi 3 ("mmap of bo N failed", "[drm] Resetting GPU")

Cause: GPU/CMA memory exhaustion. Kodi's library scanner fires ffmpeg probes for every entry in the video DB on boot — with myvideos.extractflags and myvideos.extractchapterthumbs set to true (Kodi's defaults), each probe allocates a V4L2 decoder context + scratch frames. With a few hundred large .mkv files this exhausts the 256 MiB CMA pool on the Pi in a few seconds. The kernel driver fails the mmap, the GPU is reset, and Kodi's mediacenter service restarts — only to repeat the cycle on the next boot's scan.

Symptoms: journalctl -u mediacenter shows repeated mmap of bo N (offset …, size …) failed entries; dmesg shows [drm] Resetting GPU.; kodi.log is filled with LoadFile: Failed to load ….mkv: out of memory lines.

Fix: turn off the ffmpeg-probe settings in guisettings.xml:

false
false

…then restart mediacenter.service. The EasyPlayTV sync already writes its own poster/art rows directly via SQL, so Kodi's ffmpeg-probe is not needed for the addon's library entries. Only the disk-based .mkv library (for non-addon content you also host locally) loses auto-generated thumbnails — a small price to pay for a stable boot.

Manual syncs / external triggers

JSON-RPC Addons.ExecuteAddon doesn't pass params (Kodi 21+)

Cause: Kodi 21's Addons.ExecuteAddon does not invoke python.pluginsource addons with query-string params via JSON-RPC — it loads the addon's default entry-point without forwarding argv. RunPlugin is similarly unreliable.

Fix: use the marker-file mechanism in service.py:_check_force_markers instead. Touch a file at /force_sync_ (e.g. force_sync_c4). The service polls every 30 s and fires the sync when it sees the marker; latency at worst half a minute. From a shell: touch /home/osmc/.kodi/userdata/addon_data/plugin.video.easyplaytv/force_sync_c4.

Manual sync via JSON-RPC kills the daemon thread

Cause: if you trigger ?action=sync&provider=c4 (fire-and-forget mode, no blocking=1) over JSON-RPC, the daemon thread spawned dies the moment the calling script returns — JSON-RPC RunPlugin tears down the interpreter that owns the daemon.

Fix: always use ?action=sync&provider=c4&blocking=1 from JSON-RPC, OR use the marker-file approach above. From the addon's own UI menu it's fine without blocking because the navigation thread isn't torn down.
